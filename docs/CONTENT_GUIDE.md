# 内容维护与定时会话说明

模型负责查资料、选题、判断和写作；网站负责统一排版。文章可以是短笔记，也可以是完整教程，结构由内容决定，不机械填模板。

## 四个栏目

| category | 栏目 | 选题方向 |
| --- | --- | --- |
| `news` | AI 资讯 | 模型、AI 编程工具、Agent、自动化、多模态与重要开源动态；交代事实、实际价值与独立游戏开发影响 |
| `learn` | AI 学习 | 可复现教程、工作流和案例；说明必要条件、操作过程与结果验证。常青知识不包装成当天新闻 |
| `tools` | 游戏工具 | 引擎、素材、动画、音频、关卡、UI、插件与发行工具；介绍用途、限制、上手建议与可信来源 |
| `ideas` | 游戏创意 | 真实案例、市场分析或原创构想；明确区分三者。重视核心循环与能验证它的 MVP |

不要求每天每栏都有新增。优先少而可靠、有实际价值的内容。可以迭代旧教程，不为更新日期重复发布同一篇。

## 真实性与写作

- 使用官方发布说明、项目仓库、官方文档或可靠媒体，打开来源核对日期与具体信息。搜索摘要只作线索。
- 事实、编辑推断与原创设定应能明确区分。不能编造版本、功能、报价、发布日、销量或市场结论。
- 确认不了的价格与授权标“未知”，不要把软件开源、模型许可和生成素材商用权混为一谈。
- 不能声称完成了没有运行过的教程或测试。说明实际验证范围和复现条件。
- 工作量可以给区间，但明确它是基于什么规模、经验和功能边界的估计，不是承诺。
- 游戏创意中的 AI 参与环节、最小原型、市场与风险按需要展开。没有数据支持时就写待验证假设。
- 原创构想的参考文档只是技术参考，不能用来证明市场潜力。真实游戏案例引用该游戏的官方资料。
- 保留已发布历史内容与固定链接。更正错误时透明说明更正，不悄悄删除整篇文章。

## 数据结构

编辑 `data/news.json` 中的 `items`。不重建整个文件，不覆盖其他条目。每篇基础字段：

```json
{
  "id": "learn-inventory-acceptance-20261021",
  "category": "learn",
  "type": "实战教程",
  "label": "AI 编程",
  "date": "2026-10-21",
  "title": "具体、清晰的标题",
  "summary": "一句话说明读者能得到什么。",
  "tags": ["测试", "游戏开发"],
  "blocks": [
    {"type": "heading", "text": "这一篇要解决什么问题"},
    {"type": "paragraph", "text": "写实际内容。章节名称和顺序由作者决定。"},
    {"type": "steps", "items": ["第一步的具体操作", "第二步与结果验证"]}
  ],
  "sources": [
    {"title": "来源页面的标题", "url": "https://example.org/replace-with-verified-source", "accessed": "2026-10-21"}
  ]
}
```

上面是**格式示例，不是可直接发布的文章**。必须替换正文与来源。ID 一旦发布不改变，使用小写字母、数字与连字符，3–96 字符。日期采用北京时间 `YYYY-MM-DD`：新闻用已核实的事件/发布时间，教程、工具档案和原创构想用本站编写日期。修订可以记录 `revised`，不要为了排序改写原始日期。

`type` 是读者看到的内容性质，例如“新闻”“实战教程”“工具档案”“版本更新”；创意栏目使用“原创构想”“真实游戏案例”或“市场分析”。`label` 是较稳定的主题分类，不建议把每篇文章的阅读时长塞进分类。

原有 `facts`、`value`、`action` 简短字段继续兼容。新增文章优先使用 `blocks` 自由组织正文。有 `blocks` 时它作为完整正文，旧字段不再重复显示；扩写旧文要把有价值的信息纳入新正文。

### 可用正文块

| type | 字段 | 展示 |
| --- | --- | --- |
| `heading` | `text`，可选 `level: 3` | 正文二级/三级标题 |
| `paragraph` | `text` | 段落；支持字符串中的换行 |
| `list` | `items: [字符串]` | 无序列表 |
| `steps` | `items: [字符串]` | 有序步骤 |
| `code` | `text` | 保留换行的代码块，可横向滚动 |
| `quote` | `text` | 引用块；需注明来源，遵守引用长度限制 |
| `link` | `text`, `url` | HTTPS 链接 |
| `image` | `src`, `alt`，可选 `caption` | 图片与说明 |

这些字段是纯文本，不支持内嵌 HTML 或 Markdown 语法。需要链接就添加 link 块，避免把 Markdown 原样显示给读者。图片使用已授权的 HTTPS 地址，或仓库 `assets/` 中的文件（如 `./assets/example.webp`），控制大小，避免下载大体积无用素材。

### 封面与两种阅读模式

网站默认图文网格，也提供纯文字列表，选择保存在当前浏览器。每篇可选：

```json
"cover": {
  "src": "./assets/covers/example.webp",
  "alt": "说明图片实际展示了什么"
}
```

上例路径只是格式说明，使用前要添加真实文件。优先使用有授权的产品图、游戏截图或有信息价值的原创插画。不要把概念插画当成产品截图或新闻现场照片。当前 `assets/covers/` 中的 SVG 均是本项目的主题示意图，不是官方截图。新文章没有单独封面时会显示栏目示意图，远程图片加载失败也会退回栏目图。

封面推荐 16:10 或 16:9、宽度 800–1200px，优先 WebP/AVIF，控制在约 200KB 内。正文配图仍放在 `blocks` 的 image 块中；封面不是必须塞进正文的大 Banner。没有可靠授权的图片可以不放，不能盗用第三方图片凑封面。

### 工具资料（可选）

`tool` 可含 `platforms`、`pricing`、`license` 三个字符串，前端显示为紧凑资料表。缺失字段显示“未知 · 尚未核实”。填写已知值时在 `sources` 中提供直接支持该信息的可靠页面，并记录 `accessed`；功能、优缺点、场景和建议放正文。

### 旧链接、收藏与去重

- 不修改已有 `id`，不重用删除文章的 ID，不按数组下标建链接。
- `legacyIndex` 仅映射重构前的 25 条旧链接，新增文章不写这个字段。
- 新增前按来源 URL、版本、标题与核心事件检查全库。不同栏目引用同一官方文档不一定重复；同一新闻换个标题通常仍是重复。
- 顶层 `updated` 记录内容实际维护日期，不能用“运行过任务”冒充“内容有更新”。
- 旧新闻的 `verification: "unreviewed"` 表示待复核。真正核实来源和内容后才移除该状态，不批量清除来隐藏提示。

## 发布流程

1. 确认当前分支与工作区，拉取远端最新数据，避免覆盖其他会话内容。
2. 先查阅已有文章，再收集来源、撰写与自查；没有值得发布的新内容可以不提交。
3. 执行 `npm run check` 和 `npm test`，检查新增正文、引用、图片与固定链接。
4. 本地浏览新增文章，尤其手机长标题、代码、列表和图像。
5. 在用户已授权的范围内提交并推送。发生冲突时按稳定 ID 合并，不能用整文件覆盖或强制推送解决。
6. 检查 GitHub Pages 部署结果，打开原地址确认出现新增内容，再汇报本次新增与失败项。
